# 마이크로벤치 계측·실행 시간 분리 결과

2026-09-26, a4 (Ryzen 9 7950X), Node v24.14.1. 전체 444개 사례를 각 도구에서 새 프로세스로 워밍업 1회, 측정 3회 실행했다. 아래 비교는 세 도구가 모든 반복에서 정상 완료한 **공통 422개 사례**를 사용한다.

## 계측과 실행

단위: ms, 3회 측정의 평균. 계측은 Babel 변환을 제외한 코드 생성 함수 시간이다.

| 도구 | 계측 | 동기 본문 | 본문 시작 → 이벤트 루프 유휴 |
|---|---:|---:|---:|
| 일반 Node | 0.000 | 0.016 | 0.049 |
| DynaJS | 4.319 | 0.855 | 1.531 |
| NodeMedic | 10.870 | 2.129 | 3.395 |

동기 본문은 마지막 최상위 줄까지의 시간이다. 유휴 상태까지의 구간에는 비동기 연속 실행과 이벤트 루프/로더 대기도 포함되므로 순수 JavaScript CPU 실행 시간은 아니다. **동기 본문 시간은 유휴 구간에 포함되며 둘을 더하지 않는다.**

## 전체 시간의 구성

모든 열은 위와 같은 422개 사례 기준이다. 계측 함수 바깥의 파일 입출력, 런타임 로딩, V8 컴파일, 프로세스 시작·종료, 계측 로그 출력 등은 기타에 포함된다.

| 도구 | 전체 | Babel 초기화 | Babel 변환 | 계측 | 실행~유휴 | 기타 |
|---|---:|---:|---:|---:|---:|---:|
| 일반 Node | 19.629 | 0.000 | 0.000 | 0.000 | 0.049 | 19.580 |
| DynaJS | 72.800 | 0.000 | 0.000 | 4.319 | 1.531 | 66.951 |
| NodeMedic | 286.569 | 208.016 | 9.359 | 10.870 | 3.395 | 54.928 |

이번 실행에서는 본문 실행 중 추가 계측이 발생하지 않아 위 구간을 중복 없이 합산할 수 있다(반올림 오차 제외). 일반적인 eval/dynamic import 등의 경우 계측이 실행 구간에 겹칠 수 있으므로, CSV에는 겹친 시간도 별도 기록한다.

## 측정 경계와 검증

- DynaJS: `instrument()` 함수 진입부터 반환/예외까지 측정했다. ESM 로더 스레드에서도 동기 stderr 마커로 기록한다.
- NodeMedic: Jalangi의 `instrumentCode()` 진입부터 반환/예외까지 측정하고, 내부에서 수행된 Babel 변환 시간을 뺐다. 파싱·AST 처리·코드 생성·source-map bookkeeping은 포함하고, 호출자에서 수행하는 파일 읽기·쓰기는 제외한다.
- 실행: 기존 벤치마크의 `performance.now()` 시작·종료 구문은 그대로 사용한다. 별도의 preload가 `beforeExit` 시각을 저장하고, 종료할 때 기존 타임스탬프를 읽는다. 분석 대상에 새 함수 호출을 추가하지 않는다.
- 초기 진단에서 분석 대상에 넣은 타이머 함수 호출이 일부 DynaJS built-in 사례에 약 10ms를 더하는 현상을 발견했다. 기존/새 타이머와 기존/계측 빌드를 교차 비교해 원인을 분리했다. 그 측정은 전부 제외하고 관측 방식을 수정한 뒤 전체 재측정했다.
- 이전 실험과 444개 사례의 판정 및 종료 상태가 모두 동일하다. 반복 간 판정 차이도 없다.
- 전체 3,996회 측정에서 실행 관측 마커 누락이 없고, 분석기 실행의 계측 마커 누락도 없다. 종료 시 관측한 동기 시간과 기존 `exec_ms`는 반올림 오차 내에서 일치한다.
- NodeMedic 오류 22개, DynaJS 오류 1개이며 DynaJS 오류 사례는 NodeMedic 오류 집합에 포함된다. 실패 실행은 원시 자료에 보존하고, 완료되지 않은 실행 시간을 0으로 바꾸지 않았다.
- 원래 분석기 설치, 벤치마크, 논문 소스는 변경하지 않았다. 프로세스별 cold-run 측정이며 steady-state 성능 비교는 아니다.
