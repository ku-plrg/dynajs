# 마이크로벤치의 Babel 초기화·변환 시간 분리

2026-09-26, a4 (Ryzen 9 7950X), Node v24.14.1.
전체 taint microbenchmark 444개를 조건별 워밍업 프로세스 1회, 측정 프로세스
3회로 실행했다. 시간 계측을 넣지 않은 NodeMedic 대조군은 별도로 1회씩 실행했다.
각 실행은 새 프로세스이므로, 아래는 cold process 기준 시간이다.

**전체 평균 284.84ms 중 실제 소스 변환은 9.71ms(3.4%), Babel 초기화는
206.44ms였다. 초기화와 소스 변환을 합치면 전체 시간의 75.9%다.**

## 해석

- 소스에 대한 Babel 변환 호출만 제외하려면 **275.13ms**를 사용한다.
  이 값에는 여전히 Babel 초기화 206.44ms가 포함되어 있다.
- Babel 초기화까지 회계적으로 차감하면 **68.69ms**가 남는다. 이 값에는
  Node 시작, Jalangi 계측, 분석 초기화, 실행 및 종료 비용이 남아 있다.
- 차감 값은 **실제로 Babel을 끄고 재실행한 시간도, 순수 분석 실행 시간도
  아니다**. Babel이 바꾼 코드에 대한 Jalangi 계측·실행 비용은 그대로 남는다.
  따라서 68.69ms와 DynaJS 71.77ms만으로 분석기 속도의 우열을 단정하면 안 된다.
- 이 작은 프로그램들을 새 프로세스에서 실행하는 조건에서는 Babel 비용이
  초기화, 특히 빈 코드 워밍업에 집중된다. Table 3의 전체 시간 차이를
  소스 변환 호출의 비용만으로 설명하기는 어렵다.
- 성공한 NodeMedic 실행만 포함해도 전체 284.63ms, 초기화 206.47ms,
  소스 변환 9.27ms로 경향은 같다. 그룹별 성공 실행 평균은 JSON에 포함했다.

## 검증 및 오류 처리

- 계측 전 대조군과 계측 후의 **444개 개별 판정 및 종료 코드가 모두 동일**하다.
- 3회 반복 간 판정·종료 상태의 차이가 없다.
- 분리 측정 1,332회 모두 초기화 및 변환 시간 마커가 있으며, 각 실행에서
  실제 소스 변환 호출은 1회였다. 누락된 타이밍을 0으로 대체하지 않았다.
- NodeMedic 오류 22개, DynaJS 오류 1개로 기존 Table 3의 결과를 재현했다.
  NodeMedic confusion matrix는 TP=142, FP=88, FN=30, TN=184이고,
  DynaJS는 TP=165, FP=43, FN=7, TN=229다.
- NodeMedic 중 class public fields 2개, class static block 2개 사례에서
  Babel 변환이 예외를 냈다(4개 사례 × 3회 = 12회). 이 변환 시도와 기존
  catch 처리의 시간도 기록했다. 변환 실패와 최종 분석 오류는 별도 지표다.
- 일반 Node의 1,332회 측정은 모두 정상 종료했다.
- 전체 wall time은 계측 전 대조군 283.19ms, 계측 후 284.84ms였다.
  대조군 1회와 계측군 3회를 순차 실행했으므로 1.65ms 차이를 계측 오버헤드로
  단정하지 않는다. 시간 마커 출력 비용은 Babel 구간 밖의 전체 시간에 남는다.
